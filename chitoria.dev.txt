2. Backend Requirements (The "100% Free" Tech Stack)
To avoid hallucinations and ensure you can actually build this without paying out of pocket for servers right away, you need a modern serverless architecture. This stack is the industry standard for bootstrapping high-performance apps for free:

The Scheduler (The Core Engine): You need a way to trigger messages at exactly midnight in different time zones. Since serverless functions (like Vercel) go to sleep when not in use, you cannot run a continuous timer.

Email (Free): Resend (allows 3,000 free emails per month). Ideal for delivering the links to the reveal pages.

SMS/WhatsApp (Premium Only): Twilio. Note: SMS APIs do not have viable free tiers. You must gate SMS/WhatsApp delivery behind your paid "Premium" tier so the user's payment covers the API cost.

If the user changes the text/vibe, update the message_payload in PostgreSQL.

If the user changes the delivery date/time, this requires a complex transaction:

Call Upstash QStash API to DELETE the existing scheduled message using the saved qstash_message_id.

Create a NEW scheduled message in QStash with the new timestamp.

Update the PostgreSQL row with the new delivery_time and the new qstash_message_id.

DELETE /api/wishes/:id (Cancel/Revoke):

Must trigger the QStash delete endpoint to kill the pending webhook.

Instead of a hard SQL delete, it is often safer to do a soft delete (UPDATE wishes SET status = 'cancelled') so the user maintains a history of what they built.

Export Data: A button to download a .json file of all their scheduled wishes and contacts.

Delete Account: A red button that requires them to type their email to confirm. Offering an easy exit builds massive trust for a platform handling personal contact data.

2. Backend Requirements
Because Supabase separates authentication data (auth.users schema) from public application data (public schema) for security, you need a dedicated profile table to store these preferences.

Database Schema (Supabase Profiles)
You will create a profiles table that automatically syncs with new sign-ups.

SQL
create table public.profiles (
    id uuid references auth.users(id) on delete cascade primary key,
    display_name text,
    default_timezone text default 'UTC',
    notify_on_delivery boolean default true,
    notify_on_open boolean default true,
    created_at timestamp with time zone default now()
);

-- Trigger to auto-create a profile when a new user signs up
create or replace function public.handle_new_user() 
returns trigger as $$
begin
  insert into public.profiles (id, display_name)
  values (new.id, new.raw_user_meta_data->>'full_name');
  return new;
end;
$$ language plpgsql security definer;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute procedure public.handle_new_user();
API Endpoints (/api/settings)
PATCH /api/settings: Updates the public.profiles table when a user changes a toggle or timezone.

GET /api/export: Queries all wishes and group_contributions where user_id = auth.uid() and formats the response as a downloadable JSON blob.

DELETE /api/account: This is a sensitive operation. You cannot just delete the public.profiles row; you must delete the actual auth user. You will need to use the @supabase/supabase-js Admin API (using your secure Service Role Key on the Next.js server) to call supabase.auth.admin.deleteUser(id). Because of the ON DELETE CASCADE rules on your tables, this single action will instantly wipe their profile, all their scheduled wishes, and all group contributions, keeping you 100% GDPR compliant.
